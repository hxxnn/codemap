      todo-api 코드베이스를 팀에 소개하기 위한 7장짜리 개요입니다. 다섯 개 문서가 모두 있어 빠진 슬라이드는 없습니다.

      슬라이드 1: 이게 무엇인가

      할 일을 추가하고 목록으로 조회하는 작은 HTTP API이고, Python과 FastAPI로 만들어 uvicorn app.main:app으로 실행합니다. 데이터는 DB 없이 메모리에만 보관합니다.

      슬라이드 2: 전체 그림

      사용자 요청은 uvicorn을 거쳐 FastAPI 앱으로 들어가고, 앱 안의 메모리 목록에 저장됩니다. 외부 시스템은 없습니다.

      슬라이드 3: 어떻게 구성되어 있나

      진입, API, 저장소, 모델, 유틸의 다섯 그룹이고 파일은 app/ 아래 5개입니다.

      • todo-api — 할 일을 추가하고 목록으로 보여 주는 작은 FastAPI 서비스
        • 진입 — 앱을 만들고 라우터를 붙이는 곳
          • app/main.py — FastAPI 앱 생성과 라우터 등록
        • API — HTTP 요청을 받는 층
          • app/routes.py — POST·GET /todos 라우트
            • create_todo() — 제목을 검사하고 저장소에 넘김
            • list_todos() — 저장된 할 일을 딕셔너리 목록으로 반환
        • 저장소 — 메모리에 보관
          • app/storage.py — 모듈 전역 목록 _TODOS
            • add_todo() — 할 일을 만들어 목록에 추가
            • all_todos() — 목록의 복사본 반환
            • next_id() — 다음 id 계산
        • 모델 — 할 일 데이터 형태
          • app/models.py — Todo 데이터클래스
            • Todo.create() — 저장소에서 id를 받아 Todo 생성
            • Todo.to_dict() — 응답용 딕셔너리로 변환
        • 유틸 — 공용 보조 함수
          • app/utils.py — 시간 문자열 생성
            • now_iso() — 현재 UTC 시각을 ISO 문자열로 반환

      슬라이드 4: 어떻게 실행되나

      POST /todos는 라우트가 시각을 만들고, 저장소가 모델에게 객체 생성을 맡기는 순서로 흐릅니다. FastAPI가 처리하는 구간은 추적하지 않았습니다.

  R->>U: now_iso()
  U-->>R: ISO 시각 문자열
  R->>S: add_todo(title.strip(), created_at)
  S->>M: Todo.create(title, created_at)
  M->>S: next_id()
  S-->>M: len(_TODOS) + 1
  M-->>S: Todo
  S->>S: _TODOS.append(todo)
  S-->>R: Todo
  R->>R: todo.to_dict()
  R-)C: 딕셔너리 응답
  Note over R,C: 응답 직렬화는 FastAPI가 처리, 추적하지 않음

      슬라이드 5: 부품끼리의 의존 관계

      슬라이드 6: 핵심 설계 선택

      메모리 저장소를 작은 모듈 뒤에 두었고, 저장소와 모델은 의도적으로 순환 import합니다. 이렇게 한 이유는 코드에 없습니다 (추정)

      슬라이드 7: 어디서부터 읽을까

      README.md, pyproject.toml, app/main.py, app/routes.py 순으로 읽으면 전체 흐름이 잡힙니다.

      다루지 않은 범위

      소스 파일과 설정 파일은 모두 읽었고 빠진 범위는 없습니다. FastAPI와 uvicorn 내부 동작은 다루지 않았습니다.
