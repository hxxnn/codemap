      개요

      todo-api는 할 일을 추가하고 목록으로 조회하는 작은 HTTP API입니다. Python과 FastAPI로 만들었고 uvicorn app.main:app으로 실행합니다(README.md, pyproject.toml의 의존성 fastapi, uvicorn). 데이터는 DB 없이 프로세스 메모리에만 보관합니다.

      구조

      요청은 app/main.py의 앱에서 app/routes.py의 두 라우트(POST /todos, GET /todos)로 들어가고, 라우트는 app/storage.py에 저장·조회를 맡기고 app/utils.py에서 시각을 받아 옵니다. app/storage.py는 app/models.py의 Todo로 객체를 만듭니다. 그림은 architecture.md, 파일별 import는 dependency-graph.md, 실행 순서는 sequence-flow.md, 파일·함수 목록은 mindmap.md에 있습니다.

      핵심 설계 선택

      1. 메모리 저장소를 작은 모듈 뒤에 둠 — app/storage.py의 모듈 전역 _TODOS 리스트를 add_todo(), all_todos(), next_id() 함수로만 다룹니다. 효과: 라우트는 저장 방식을 모르지만, 재시작하면 데이터가 사라집니다. 이렇게 한 이유는 코드에 적혀 있지 않습니다 (추정: 단순한 예제라서)
      2. 저장소와 모델의 의도적 순환 import — app/storage.py와 app/models.py가 서로를 import하며, 두 파일 모두 주석에 "deliberate cycle"이라고 적혀 있습니다. 효과: Todo.create()가 storage.next_id()로 id를 받고, 저장소는 models.Todo.create()로 객체를 만드는 양방향 호출이 생깁니다. 의도적이라는 사실만 주석에 있고 이유는 없습니다 (확인 필요)
      3. 리소스 하나에 라우터 하나 — app/routes.py가 APIRouter를 만들고 app/main.py가 include_router로 붙입니다. 효과: 라우트가 늘어도 app/main.py는 거의 변하지 않습니다.
      4. 검증은 라우트 함수에서 — create_todo()가 공백뿐인 제목이면 HTTPException(422)를 던집니다. 효과: 모델과 저장소는 이미 검증된 입력만 받습니다.
      5. 데이터클래스 모델과 to_dict() — app/models.py의 Todo는 @dataclass이고 응답용 변환 메서드를 직접 가집니다. 효과: 응답 모양이 한 곳에 모입니다.

      읽는 순서

      6. app/models.py — Todo 정의와, 저장소와의 순환 import 확인
